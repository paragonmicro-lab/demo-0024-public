    Demo 1a: a cloud-native golden image¶

    Version 2.6.0 · draft · 2026-10-20 · class/demos/01a-vm-cloudnative-golden-image.md

    What you will learn¶

    In Demo 1 you moved an existing Windows VM: a pet, built once by hand in vCenter, patched in place, and copied whenever someone needs another. Here you build its replacement from scratch, in code: a CentOS Stream 10 server running the same PostgreSQL database, with its own logins, its data and its WAL (the log) on separate disks, and its services running. Nothing is installed by hand and nothing is baked into an image:

    The pet golden image (vSphere) The cloud-native golden image (OpenShift)
    Base OS an ISO you install, then keep patching yourself Red Hat's boot source, a cloud image that OpenShift Virtualization keeps up to date
    Customization clicks and scripts inside the image, then sysprep and Convert to Template a Template with cloud-init: text in git, reviewed like code
    A new server clone the template, then fix what drifted the same code, every time: identical servers in minutes
    Proof it works someone checks by hand CI deploys it on every lab build and tests it with SQL

    You deploy it twice over: in the console (as in the video), and with one command. Then you inject rows into the new Linux PostgreSQL and read them back, exactly as you did on Windows.

    Before you start: do Lab 0. You are signed in to the site A console, and your class terminal is signed in to the database (dblogin, once). Do it while Demo 1's copy runs (started in Demo 1 §1.3): this demo builds a new VM, at its own address, and Demos 1b to 1e all use it while your Windows VM is still copying: snapshot, live and storage migration, cross-cluster migration (BCDR class) and OADP backup. Commands run in the console's Web Terminal (>_).

    ⚠ The commands are an example. Change these values to yours before you run them:

    In the example Is the example's Replace with yours
    student-01-0024-012 class ID and project your class ID
    pg-s01-centos10 the new VM's name pg-s<NN>-centos10
    10.101.23.151 the new VM's address: VLAN 23, 150 + your student number 10.101.<22 + N>.<150 + NN>
    23 your booking's VLAN (22 + N, vcenter01 → 23) from your instructor's N
    student-01 / student_01 your Linux login / your database login (underscore) yours

    🎬 Demo 1a: a cloud-native golden image: a walk-through of the whole demo in the console. Watch it, then do the same with the steps below.

    1a.1 Look at the golden image: it's code¶

    The lab published the customer's Template, ovedr-centos10-postgres, on both clusters. It lives in the openshift project, the shared one, so every project's catalog offers it.

    Console (site A): first set the Project dropdown at the top to your project (student-01-0024-012), then open Virtualization → Catalog → Template catalog. Find CentOS Stream 10 + PostgreSQL 16 (class) (filter on PostgreSQL; it is a user template, not a Red Hat one). Open it: the boot source is Red Hat's CentOS Stream 10, with three disks and your VLAN's network.

    ⚠ "No Templates found"? Check the Project dropdown. On Virtualization → Templates the list shows only the project you have selected, and the Template is not in openshift-mtv or your own project: switch it to openshift (or All projects). The Template catalog does not have this problem, because it always adds the openshift project's Templates to yours.

    The same from the Web Terminal: what it asks for, and the code itself. oc process is how a Template is used from the command line. A Template is YAML with blanks in it (${NAME}, ${IP}, …): oc process --parameters lists the blanks, which are the same fields the console's form asks for. oc process -p NAME=… fills them in and prints the finished VM; it creates nothing until you pipe it to oc apply (1a.2).

    oc process --parameters -n openshift ovedr-centos10-postgres
oc get template -n openshift ovedr-centos10-postgres -o yaml | less          # q to quit
    In the Template What it does
    dataVolumeTemplates the system disk, cloned from Red Hat's centos-stream10 boot source, plus two empty disks: 10 GB for the data, 5 GB for the WAL
    networks one NIC on your VLAN's bridge (default/vmnet23), so the server has its own address on the lab network
    cloudInitNoCloud.networkData that address, its gateway and the lab's DNS
    accessCredentials your public SSH key, read from a Secret you create (parameter SSH key Secret), put on your Linux login at first boot
    a Secret <VM name>-cloudinit, read by cloudInitNoCloud.secretRef cloud-init, run on first boot: formats and mounts the two disks, installs PostgreSQL 16 with its WAL on its own disk, loads the class's marks toolkit, creates your Linux and database logins (SSH takes your key or your password), starts the database and a heartbeat

    The whole file is also on the class site: ovedr-centos10-postgres.yaml.

    1a.2 Deploy it¶

    Two steps: save your public SSH key in OpenShift, then deploy the Template. Each has a console way and a Web Terminal way, and both ways give the same result.

    Step 1: your SSH key, saved in OpenShift as a Secret¶

    A server built from code gets its SSH key the way a cloud server does: OpenShift holds your public key in a Secret in your project, and the Template hands it to the VM on its first boot. Your private key never leaves your terminal.

    Make a key pair in the Web Terminal (both ways start here, since the class installs nothing on your laptop):

    ssh-keygen -t ed25519 -N '' -C student-01 -f ~/.ssh/id_ed25519      # your key pair: no passphrase, for the lab
cat ~/.ssh/id_ed25519.pub                                            # the PUBLIC key: one line, ssh-ed25519 AAAA… student-01

    Console (site A), as in the video: Workloads → Secrets → Create → Key/value secret, in project student-01-0024-012:

    Field Value
    Secret name student-01-ssh
    Key key
    Value paste the public key line from cat ~/.ssh/id_ed25519.pub (or Browse to upload a .pub file)

    Then Create. This is the same Secret the VM wizards' Public SSH key → Add new dialog saves ("SSH key is saved in the project as a secret").

    Or, the Web Terminal:

    oc -n student-01-0024-012 create secret generic student-01-ssh --from-file=key=$HOME/.ssh/id_ed25519.pub

    ✅ secret/student-01-ssh created. Check it holds your public key, and only that:

    oc -n student-01-0024-012 get secret student-01-ssh -o jsonpath='{.data.key}' | base64 -d     # ssh-ed25519 AAAA… student-01

    Where you test it from. The console has two ways in: the VM's Console tab (your login and password: no key needed), and the Web Terminal, which has ssh, ssh-keygen and virtctl and reaches your VLAN. That is why the key pair is made in the Web Terminal: its private key is where ssh runs. A key from your laptop only works from your laptop, and the browser-only class doesn't reach the lab's VLANs from there.

    The Web Terminal has no disk of its own: when it closes or idles out (about 15 minutes), ~/.ssh is gone. A key reaches a VM only on its first boot, so a new pair won't open your server. Keep a copy of the private key in a second Secret in your project (only you and the instructor can read it), and bring it back in any new terminal:

    oc -n student-01-0024-012 create secret generic student-01-ssh-private --from-file=id_ed25519=$HOME/.ssh/id_ed25519   # once
mkdir -p ~/.ssh && oc -n student-01-0024-012 extract secret/student-01-ssh-private --to=$HOME/.ssh --confirm \
  && chmod 600 ~/.ssh/id_ed25519                                                                                      # each new terminal

    Never put the private key in student-01-ssh: every value in that Secret is handed to the VM as a public key.

    Step 2: deploy the Template¶

    Console (site A), as in the video: in the Template catalog, open CentOS Stream 10 + PostgreSQL 16 (class) → Customize VirtualMachine → project student-01-0024-012, and fill in the parameters:

    Parameter Example
    VM name pg-s01-centos10
    VLAN 23
    IP address 10.101.23.151
    Linux login student-01
    Database login student_01
    Password (Linux and database) your class password
    SSH key Secret student-01-ssh (the Secret from step 1)

    ⚠️ Check the project before you create. The VM is created in the project the wizard shows, and a VM can never change project afterwards: Kubernetes refuses to edit metadata.namespace ("Cannot change resource namespace"). It must be your project, student-01-0024-012, next to your Windows VM and your class terminal. Built it in the wrong one (default, say)? Delete it there and deploy again here: it's code, so that takes minutes and loses nothing.

    Then Create VirtualMachine. Leave the wizard's own Public SSH key setting at None: the Template already takes your key from the Secret you named. [verify: the console's Template form shows the SSH key Secret parameter]

    ⚠️ Not the InstanceTypes tab. Catalog → InstanceTypes builds a plain CentOS VM from Red Hat's boot source, with none of this Template's code: no PostgreSQL, no data disks, no class logins. Use the Template catalog. (Its N series (n1.*) is for network appliances: dedicated CPUs and 1 GiB hugepages that this lab's nodes don't offer, so such a VM stays ErrorUnschedulable.)

    Or, the Web Terminal: the whole server is one command. oc process fills in the Template's blanks, exactly as the form did, and oc apply creates the result in your project. It asks for your password, so it never appears on screen:

    read -rsp 'Your class password: ' PW; echo; oc process -n openshift ovedr-centos10-postgres -p NAME=pg-s01-centos10 -p VLAN=23 -p IP=10.101.23.151 -p OS_USER=student-01 -p DB_USER=student_01 -p DB_PASSWORD="$PW" -p SSH_KEY_SECRET=student-01-ssh | oc apply -n student-01-0024-012 -f -; unset PW

    ✅ secret/pg-s01-centos10-cloudinit created and virtualmachine.kubevirt.io/pg-s01-centos10 created.

    💡 Your cloud-init, password included, is in a Secret, pg-s01-centos10-cloudinit, in your project. The VM points at it (cloudInitNoCloud.secretRef), so the VM's definition holds no password. A Secret is also the only way for a real server: KubeVirt refuses cloud-init written inline in the VM above 2 KB, and this one is about 11 KB. The Template creates both, so both are yours to delete (1a.5).

    Build it yourself in the console: your own Template, your own cloud-init (optional)

    The class's Template did the work above. Here you make your own Template in the console: clone one of Red Hat's templates, point it at the CentOS Stream 10 boot source, give it a short cloud-init (the standard way a cloud server is customized on its first boot) and your network, then create the server from it. The PostgreSQL build itself (install, the class database and toolkit, your database login, the heartbeat) is the lab's published script, ovedr-pg-setup.sh: your cloud-init downloads and runs it, so you write 30 lines, not 300. Read the script first: it is what will run as root on your server.

    One address per student: build this instead of the Template's server, or delete that one first (1a.5), since both would use 10.101.23.151. Like the Template's server, yours keeps PostgreSQL's data and its WAL (the write-ahead log) on two disks of their own, which you add in step 4: data 5 GiB, WAL 1 GiB (the Template's are 10 and 5). Demos 1b – 1e work on either; 1c moves your 5 GiB data disk.

    Where the cloud-init goes. The console's cloud-init editor does not hold a plain #cloud-config file. It edits the VM's cloud-init disk, which has two fields, each a text block:

    • userData: |: the cloud-init itself (users, packages, files, commands). KubeVirt allows at most 2 KB inline.
    • networkData: |: the network settings (address, gateway, DNS).

    So below is one block, in exactly that shape. It replaces everything in the editor, including the default user: centos and the generated password. Keep the two-space indent under each field: it is what makes the lines part of that field. Paste a bare #cloud-config instead and the console refuses it with unknown field "...cloudInitNoCloud.hostname" (and runcmd, packages, and so on).

    Console (site A): [verify: the field names on OpenShift 4.19's console]

    1. Set the Project dropdown to your project, student-01-0024-012.
    2. Virtualization → Templates, project All projects, filter centos. OpenShift 4.19 has a CentOS Stream 10 boot source but no CentOS Stream 10 template (ovedr-centos10-postgres is the class's own), so start from the nearest one: centos-stream9-server-small → ⋮ → Clone.
    3. Template name pg-s01-centos10-template, Template project your project, student-01-0024-012 (the dialog offers openshift first: change it). A template can't change project later, and the Secrets its tabs make land in its project. A VM in your project can't read a Secret in openshift: it would wait at Starting for good (debug guide: Starting, secret … not found).
    4. Display name pg-s01 PostgreSQL (CentOS Stream 10).
    5. Leave Clone the boot source unticked: your template uses the shared boot source, as the class's does.
    6. Point your template at CentOS Stream 10. Open it (Virtualization → Templates, project student-01-0024-012) → YAML. Red Hat's templates take their boot disk from a parameter, near the end:
      - name: DATA_SOURCE_NAME
    description: Name of the DataSource to clone
    value: centos-stream9          # → centos-stream10

    Change centos-stream9 to centos-stream10 in that one place, then Save. That is the whole difference between the two templates' operating systems: the boot source centos-stream10, in project openshift-virtualization-os-images, which OpenShift keeps up to date. (The template's labels still say CentOS Stream 9; that only affects how the console lists it.) 4. Still in your template, set it up, tab by tab: - Network: edit the NIC → network default/vmnet23 (your VLAN's bridge), type Bridge. - Disks → Add disk, twice, both Blank, interface virtio, the default storage class: pgdata, 5 GiB, for PostgreSQL's data; pgwal, 1 GiB, for its log (the WAL). Then give each a serial equal to its name, which is how cloud-init finds it (/dev/disk/by-id/virtio-pgdata): on the YAML tab, under spec.template.spec.domain.devices.disks, add serial: pgdata to the pgdata entry and serial: pgwal to the pgwal entry, then Save. [verify: whether 4.19's Add disk form has a Serial field] - Scripts → Cloud-init → Edit → Script. Select all (Ctrl-A / ⌘-A), delete, paste the block below, change the lines marked ✎, then Save. Stay in Script: switching back to Form view rebuilds the simple form and drops what it can't show. - Scripts → Public SSH key → Edit → Use existing → student-01-ssh (the Secret from step 1 above), not Add new. - Details → CPU | Memory: 1 CPU, 4 GiB (PostgreSQL wants more than the small template's 2 GiB). 5. ⋮ → Create VirtualMachine (or Catalog → Template catalog → User templates → yours). Change the generated name (centos-stream10-…) to pg-s01-centos10, then Create VirtualMachine. Demos 1b – 1e name the VM in their commands, and a VM can't be renamed. Carry on with 1a.3 as for the Template's server.

    Edit the template, not a VM made from it: cloud-init runs only on a VM's first boot, so changing a VM's cloud-init after it has started does nothing. A wrong template is cheap: fix it, delete the VM, create it again.

    The block to paste: about 1.9 KB, all of it saved in your template's definition.

    userData: |
  #cloud-config
  # Demo 1a, built yourself: the class's PostgreSQL server from a plain CentOS Stream 10 VM.
  hostname: pg-s01-centos10                     # ✎ your VM's name
  system_info:
    default_user:
      name: student-01                          # ✎ your Linux login (your SSH key lands here too)
      groups: [ wheel ]
      sudo: [ "ALL=(ALL) NOPASSWD:ALL" ]
      lock_passwd: false
  users: [ default ]
  ssh_pwauth: true                              # SSH with your password as well as your key
  chpasswd:
    expire: false
    users:
      - { name: student-01, password: "<your class password>", type: text }   # ✎ your login and password
  fs_setup:                                     # your two disks (step 4), found by serial
    - { device: /dev/disk/by-id/virtio-pgdata, partition: none, filesystem: xfs, label: pgdata }
    - { device: /dev/disk/by-id/virtio-pgwal, partition: none, filesystem: xfs, label: pgwal }
  mounts:
    - [ LABEL=pgdata, /var/lib/pgsql/data, xfs, "defaults,nofail,context=system_u:object_r:postgresql_db_t:s0" ]
    - [ LABEL=pgwal, /var/lib/pgsql/wal, xfs, "defaults,nofail,context=system_u:object_r:postgresql_db_t:s0" ]
  packages: [ postgresql-server, qemu-guest-agent ]
  write_files:
    - path: /root/.ovedr-db                     # read once by the setup script, then shredded
      permissions: "0600"
      content: |
        DB_USER=student_01
        DB_PASSWORD=<your class password>
  runcmd:
    # the class's PostgreSQL build, published on the class site: read it before you run it
    - curl -fsSL -o /usr/local/sbin/ovedr-pg-setup https://paragonmicro-lab.github.io/demo-0024-public/downloads/ovedr-pg-setup.sh
    - bash /usr/local/sbin/ovedr-pg-setup
networkData: |
  version: 2
  ethernets:
    enp1s0:
      addresses: [ 10.101.23.151/24 ]                  # ✎ 10.101.<VLAN>.<150 + your number>
      routes: [ { to: 0.0.0.0/0, via: 10.101.23.1 } ]  # ✎ your VLAN's gateway, 10.101.<VLAN>.1
      nameservers: { addresses: [ 10.101.6.201, 10.101.6.202 ] }

    Your values: VM name pg-s<NN>-centos10; Linux login student-<NN>; database login student_<NN> (underscore); password: your class password, in both places; address 10.101.<VLAN>.<150 + NN>; gateway 10.101.<VLAN>.1.

    What each part does, the same jobs the Template's cloud-init does:

    cloud-init What it does
    hostname the server's name inside Linux
    system_info.default_user, users makes your Linux login the VM's default user, in wheel (sudo); your SSH key from the Secret lands on it
    ssh_pwauth, chpasswd SSH and the console accept your password too
    fs_setup, mounts formats your two disks (xfs) and mounts them where PostgreSQL keeps its data and its WAL, with PostgreSQL's SELinux label; the script then puts the WAL on its own disk
    packages installs PostgreSQL and the QEMU guest agent from the CentOS mirrors
    write_files your database login and password, in a root-only file the script reads once and then shreds
    runcmd downloads the class's setup script and runs it; its last line in /var/log/cloud-init-output.log is OVEDR-READY
    networkData a fixed address on enp1s0 (the VM's NIC on your VLAN), the gateway, and the lab's DNS

    Compare yours with the class's. Open your template's YAML tab next to the class's Template: the same VM, NIC and cloud-init disk. Its Secret ${NAME}-cloudinit carries the same #cloud-config with the PostgreSQL build written inline, and its VM's cloudInitNoCloud has the same networkData. What you pasted by hand is what the Template fills in from its parameters. Learn the rest of cloud-init later, from the cloud-init module reference and KubeVirt's cloud-init guide.

    Your password is in your template's definition this time (cloud-init written in the console stays inline). The class's Template keeps it in a Secret; for a lab login that dies with the booking, either is fine.

    1a.3 Watch it build itself¶

    Console: Virtualization → VirtualMachines → pg-s01-centos10. It goes Provisioning (the disks are created: the system disk is cloned from the boot source), Starting, then Running.

    oc -n student-01-0024-012 get dv                                     # pg-s01-centos10, -pgdata, -pgwal: Succeeded
oc -n student-01-0024-012 get vmi pg-s01-centos10 -w                 # Running (Ctrl-C to stop watching)

    Once it is Running, cloud-init installs and configures PostgreSQL: allow a few minutes. Open the VM's Console tab and log in as student-01 with your class password, then:

    cloud-init status --wait                                 # status: done
lsblk -o NAME,SIZE,LABEL,MOUNTPOINT                      # vdc pgdata /var/lib/pgsql/data · vdd pgwal /var/lib/pgsql/wal
systemctl is-active postgresql ovedr-heartbeat           # active, active
sudo ls -l /var/lib/pgsql/data/pg_wal                    # → /var/lib/pgsql/wal/pg_wal: the WAL on its own disk

    ✅ cloud-init done, both database disks mounted, both services active. Every one of these was declared in the Template, and none was typed by hand.

    Sign in over SSH, from the Web Terminal: first with your key, then with your password. Both work, because the Template turned on both.

    ssh -o StrictHostKeyChecking=accept-new student-01@10.101.23.151 'hostname; whoami'                          # key: no password asked
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password student-01@10.101.23.151 'whoami'       # password: asks for it

    ✅ The first prints pg-s01-centos10 and student-01 without asking anything: your key from the Secret is in ~/.ssh/authorized_keys. The second asks for your class password, then prints student-01. (Also works through the API server, without reaching the VLAN: virtctl ssh -n student-01-0024-012 -i ~/.ssh/id_ed25519 student-01@vm/pg-s01-centos10.)

    1a.4 Inject into your new Linux PostgreSQL, and read it back¶

    Same commands as on Windows, at the new address. Your class terminal's dblogin works here too: same login, same password, a different server.

    oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -c "SELECT * FROM ovedr_mark('student-01-0024-012', 'cloudnative-started', 'Demo 1a: CentOS Stream 10 from the Template');"
oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -c "SELECT * FROM ovedr_load('student-01-0024-012', 'cloudnative-load', 100);"
oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -c "SELECT id, ts, stage, payload FROM marks ORDER BY id;"
oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -c "SELECT * FROM ovedr_verify('student-01-0024-012');"

    ✅ The read-back starts fresh at cloudnative-started, then your 100 cloudnative-load rows, and ovedr_verify shows chain_ok = t. A new server has a new database: your Windows VM's rows are still on your Windows VM.

    Is it alive, and what is it?

    oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -c "SELECT count(*) AS beats, date_trunc('second', clock_timestamp() - max(ts)) AS staleness FROM heartbeat;"
oc exec -n student-01-0024-012 deploy/sql-client -- sql -h 10.101.23.151 -x -c "SELECT version(); SELECT platform, qemu_ga, virtio FROM guest_tools ORDER BY id DESC LIMIT 1;"

    ✅ staleness under 10 seconds, PostgreSQL 16 on Linux, platform kvm, QEMU guest agent active, virtio drivers: the same checks as your migrated Windows VM, on a server that was never migrated.

    1a.5 Rebuild it: the point of a golden image as code¶

    A pet is repaired. Cattle are replaced. Delete the server and deploy it again from the same Template:

    oc -n student-01-0024-012 delete vm,secret -l app=pg-s01-centos10    # the VM, its three disks and its cloud-init Secret

    Your SSH key Secret student-01-ssh stays (it isn't labelled with the VM), so the rebuild reuses it.

    Then run 1a.2 again. In a few minutes you have the same server at the same address, with an empty marks table: every setting came from code, so nothing drifted and nothing was forgotten.

    That is the end of Demo 1a. You built a database server purely in code, from Red Hat's maintained image, and proved it with your own rows. Keep it running (redeploy it if you deleted it above): Demos 1b to 1e use it.

    💡 One copy at a time on an address. 10.101.23.151 is yours alone. When you've finished Demo 1e, go back to Demo 1 §1.4 and stop pg-s01-centos10 there (no need to delete it).

    1a.6 Explore: a one-off VM from the Catalog (optional)¶

    Everything so far went through a template: written once, reviewed, then deployed the same way every time. The console's Catalog is the other way in: pick an OS, click, and you have a VM. That is right for a quick test box; nothing records how it was built, so the next one may come out different.

    Console (site A):

    1. Project student-01-0024-012, then Virtualization → Catalog → InstanceTypes.
    2. Pick any boot volume the lab offers (Red Hat's catalog: CentOS Stream, Fedora, RHEL…), series U series, size u1.small. Name it explore-s01.
    3. Look at what Customize VirtualMachine would let you change (the same tabs as your template's), then simply Create VirtualMachine: it uses the pod network and a generated login, so it takes no lab address.
    4. When it is Running: Overview shows the login (user and the generated password), the Console tab logs you in. Look around, then Actions → Delete: the lab's capacity is shared.

    ✅ Two ways to the same kind of VM: the Catalog for a one-off, a Template for a server you will build again, and again, the same way. Your template from the twisty above sits in the Catalog too, under Template catalog → User templates: a template is how a one-off becomes a standard.

    Addendum: how the lab staged this demo, as code¶

    CI job Code What it does
    golden-linux automation/customize/golden_linux.sh builds the Template and applies it to namespace openshift on every site that has the CentOS Stream 10 boot source
    (same job) the proof deploys a test VM from the Template (ovedr-ci-centos10, 10.101.<VLAN>.98), waits for PostgreSQL, writes a mark, checks chain_ok, the heartbeat and the guest tools, then deletes the VM. The run's summary shows how long the server took to answer
    (build) automation/tools/centos10_template.sh assembles the Template from one cloud-init file (workload/centos10/user-data.yaml) and the class's SQL (workload/sql/), the same schema and toolkit the Windows VMs run. A test fails if the published copy differs from what it builds

    The customer's version of this is a short pipeline: change the cloud-init in git → CI builds the Template, deploys a test VM, runs its checks → the Template is published for everyone. The base OS comes from Red Hat's boot source, which OpenShift Virtualization updates on its own; your code stays the same.
