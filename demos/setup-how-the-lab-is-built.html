    Lab S: How this lab was built¶

    Version 0.6.2 · draft · 2026-10-15 · class/demos/setup-how-the-lab-is-built.md

    What you will learn¶

    Before your class started, a CI pipeline built three environments and then customized them: operators, networks, storage, migration providers and maps, a namespace with a database client, one Windows + PostgreSQL VM per student, and a staged migration plan for each VM. This guide walks through every one of those pieces in the order CI builds them. For each piece you see what was built, how to check it, how to build it yourself from the command line, and how to do the same in the console, with links to the Red Hat documentation that describes it. The demo guides only ask you to do the last step yourself (start your migration). This guide is how you would do everything before it.

    How the lab is set up¶

    Built by What Where
    demo-vmware (core-web dispatches it) vCenter vcenter0<N>, 4 nested ESXi hosts, the shared NFS datastore coresan01_data00, port group vm-network on VLAN 22+N, your vCenter folder vms/students/<your ID> vSphere lzN
    demo-openshift (core-web dispatches it, twice) OpenShift 4.19, OpenShift Virtualization (ove: cnv), ACM and cert-manager, NMState bridges + NADs per VLAN, nfs-csi storage; ODF on site A only site A <A> and site B <B>
    this demo's CI (customize, sections S.5–S.12) MTV, providers, maps, the class namespace, the class VMs, demo prep, the staged plans all three
    you start your own migration plan (Demo 1 / 1b), then everything in the demo guides

    Picture: lab diagram. Every command below uses your class terminal's variables ($A, $B, $N, $VM, $DOMAIN; Toolkit T.1) and the contexts site-a / site-b. Most "do it yourself" steps need cluster-admin. In class you only read these objects; the instructor (or a cluster you own) can run the build steps.

    export VLAN=$((22 + N))                 # the vSphere zone's VLAN: also the bridge your migrated VM can join

    S.1 The three environments, and what both clusters should look like¶

    What CI built: core-web booked one vSphere zone and two OpenShift clusters together. Both clusters are built from the same member selections (ove: cnv, ACM, cert-manager), so they carry the same operators. The one difference is storage: the lab has four scratch SSDs, enough for one ODF cluster, so site A runs ODF and site B uses NFS (nfs-csi). The healthcheck compares the two sites' operators and reports any difference (ODF excluded).

    Check:

    for s in site-a site-b; do echo "== $s"; oc --context $s get csv -A --no-headers \
  | awk '{print $2}' | sed 's/\.v\{0,1\}[0-9].*$//' | sort -u; done
oc --context site-a get storageclass; oc --context site-b get storageclass

    Console: Operators → Installed Operators, project All Projects, on each site. 📸 S-operators-site-a · 📸 S-operators-site-b: the two installed-operator lists side by side.

    Red Hat docs: - OpenShift Container Platform 4.19 documentation - Operators: understanding OLM and installed operators - About OpenShift Virtualization

    S.2 OpenShift Virtualization (built by demo-openshift)¶

    What was built: the OpenShift Virtualization operator (kubevirt-hyperconverged) in openshift-cnv, and its HyperConverged resource kubevirt-hyperconverged. That resource deploys KubeVirt, CDI (the disk importer), the templates and the boot sources.

    Check:

    oc --context site-a -n openshift-cnv get hyperconverged kubevirt-hyperconverged \
  -o jsonpath='{.status.conditions[?(@.type=="Available")].status}{"\n"}'      # True
oc --context site-a -n openshift-cnv get csv | grep -i kubevirt

    Do it yourself (CLI):

    oc apply -f - <<'YAML'
apiVersion: v1
kind: Namespace
metadata: { name: openshift-cnv }
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata: { name: kubevirt-hyperconverged-group, namespace: openshift-cnv }
spec: { targetNamespaces: [ openshift-cnv ] }
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata: { name: hco-operatorhub, namespace: openshift-cnv }
spec: { source: redhat-operators, sourceNamespace: openshift-marketplace, name: kubevirt-hyperconverged, channel: stable }
YAML
# once the CSV says Succeeded:
oc apply -f - <<'YAML'
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata: { name: kubevirt-hyperconverged, namespace: openshift-cnv }
spec: {}
YAML

    Console: 1. Operators → OperatorHub → search OpenShift Virtualization → Install (namespace openshift-cnv). 📸 S-cnv-operatorhub 2. Installed Operators → OpenShift Virtualization → Create HyperConverged → Create. 📸 S-cnv-hyperconverged 3. A Virtualization menu appears in the left navigation. 📸 S-cnv-menu

    Red Hat docs: - Installing OpenShift Virtualization - Preparing your cluster for OpenShift Virtualization [verify link] - OpenShift Virtualization architecture [verify link]

    S.3 Networking: VLANs to bridges to network attachments¶

    What was built (demo-openshift): the Kubernetes NMState operator, and on every node a Linux bridge br<VLAN> on the trunk NIC for each lab VLAN. Each bridge is a NodeNetworkConfigurationPolicy (NNCP) named br<VLAN>-policy. In default there is a NetworkAttachmentDefinition (NAD) vmnet<VLAN> that lets a VM plug into that bridge. The VLAN is the same one the vSphere port group vm-network uses, so a migrated VM can keep its address.

    vSphere OpenShift
    port group vm-network, VLAN 22+N NNCP br<22+N>-policy → bridge br<22+N> → NAD default/vmnet<22+N>

    Check:

    oc --context site-a get nncp                                                   # br<VLAN>-policy … Available
oc --context site-a get nncp "br${VLAN}-policy" -o jsonpath='{.status.conditions[?(@.type=="Available")].status}{"\n"}'
oc --context site-a -n default get net-attach-def "vmnet${VLAN}" -o jsonpath='{.spec.config}{"\n"}' | jq .

    Do it yourself (CLI): install Kubernetes NMState Operator from OperatorHub, create its NMState instance, then:

    TRUNK='<trunk NIC on the nodes, e.g. ens224>'          # [verify] the trunk interface name on your nodes
oc apply -f - <<YAML
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata: { name: br${VLAN}-policy }
spec:
  desiredState:
    interfaces:
      - name: ${TRUNK}.${VLAN}
        type: vlan
        state: up
        vlan: { base-iface: ${TRUNK}, id: ${VLAN} }
      - name: br${VLAN}
        type: linux-bridge
        state: up
        ipv4: { enabled: false }
        bridge: { options: { stp: { enabled: false } }, port: [ { name: ${TRUNK}.${VLAN} } ] }
---
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata: { name: vmnet${VLAN}, namespace: default }
spec:
  config: '{"cniVersion":"0.3.1","name":"vmnet${VLAN}","type":"bridge","bridge":"br${VLAN}","macspoofchk":true}'
YAML

    Console: 1. Networking → NodeNetworkConfigurationPolicy → Create (form or YAML), as above. 📸 S-nncp-create 2. Wait for Available on every node. 📸 S-nncp-available 3. Networking → NetworkAttachmentDefinitions → Create in default: type Linux bridge, bridge name br<VLAN>. 📸 S-nad-create

    Red Hat docs: - Kubernetes NMState operator [verify link] - Connecting a VM to a Linux bridge network [verify link] - Multiple networks: NetworkAttachmentDefinition [verify link]

    S.4 Storage: whatever the booking chose, and snapshot classes¶

    Storage is not this demo's choice. demo-openshift deploys each cluster's storage from its storage option (na = NFS, odf; other storage providers such as Portworx are forks of this class, BL-D25) and marks the class VMs belong on. CI's customize only reads that class (the storageclass.kubevirt.io/is-default-virt-class one, else the cluster default) and proves a test claim binds before any VM lands there. The demos work the same on any of them: they are about migration and BCDR.

    # the class your VMs land on, per site (what CI's sc_live reads)
for s in site-a site-b; do
  oc --context $s get sc -o jsonpath='{range .items[?(@.metadata.annotations.storageclass\.kubevirt\.io/is-default-virt-class=="true")]}{.metadata.name}{"\n"}{end}'
done

    What this booking's build has today: - Site A: OpenShift Data Foundation (ODF), Ceph on the four scratch SSDs. VMs use the storage class ocs-storagecluster-ceph-rbd-virtualization (block, RWX, so live migration works). Built by demo-openshift (storage: odf); core-web reserves the SSDs for the booking. - Site B: nfs-csi on the lab NFS server (demo-openshift's default). - Snapshot classes come with the storage, from demo-openshift: nfs-csi-snapclass (driver nfs.csi.k8s.io) and ODF's own. Demo 1's snapshot bonus needs one. CI's demo-prep only reports a VM storage driver without one.

    Check:

    oc --context site-a get storageclass ocs-storagecluster-ceph-rbd-virtualization
oc --context site-a -n openshift-storage get storagecluster      # Ready
oc --context site-b get storageclass nfs-csi
for s in site-a site-b; do oc --context $s get volumesnapshotclass; done

    Do it yourself (CLI): a snapshot class for a driver that has none (what demo-openshift creates for NFS):

    oc --context site-b apply -f - <<'YAML'
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata: { name: nfs-csi-snapclass }
driver: nfs.csi.k8s.io
deletionPolicy: Delete
YAML

    ODF itself: install the OpenShift Data Foundation operator, label the storage nodes, and create a StorageSystem / StorageCluster on the local SSDs (the Local Storage operator discovers them).

    Console: 1. Operators → OperatorHub → OpenShift Data Foundation → Install. 📸 S-odf-install 2. Storage → Data Foundation → Create StorageSystem → Create a new StorageClass using local storage devices. 📸 S-odf-storagesystem 3. Storage → StorageClasses: see ocs-storagecluster-ceph-rbd-virtualization (site A) and nfs-csi (site B). 📸 S-storageclasses 4. Storage → VolumeSnapshotClasses → Create. 📸 S-snapclass

    Red Hat docs: - Deploying ODF using local storage devices [verify link] - Storage for virtual machines [verify link] - CSI volume snapshots [verify link]

    S.5 The Migration Toolkit for Virtualization (MTV) operator¶

    Who built it: the booking's migration_tools decides which sites get MTV (both: site A and site B; site-a: site B is left bare so students install MTV there). On those sites demo-openshift installs it (ove: cnv-mtv), and CI (ansible/roles/mtv_operator) checks it and customizes it for the class: - (demo-openshift) Namespace openshift-mtv, OperatorGroup migration (targets openshift-mtv), and Subscription mtv-operator: channel release-v2.11, source redhat-operators. CI waits for the CSV to report Succeeded. - (demo-openshift) ForkliftController/forklift-controller with feature_ui_plugin, feature_validation, feature_volume_populator and feature_must_gather_api all "true". (CI) adds controller_precopy_interval: "5" for Demo 2 and waits for deploy/forklift-controller to be Available. - (demo-openshift; CI re-checks) MTV's console plugin enabled in consoles.operator.openshift.io/cluster → spec.plugins. This is what adds the Migration for Virtualization menu. - Class access: RoleBinding ovedr-students-view (ClusterRole view) and Role + RoleBinding ovedr-students-migrate. The second lets students create, start and delete plans and migrations, and only read providers, maps and hosts. It never grants secrets.

    Check:

    oc --context site-a -n openshift-mtv get subscription mtv-operator -o jsonpath='{.spec.channel}{"\n"}'   # release-v2.11
oc --context site-a -n openshift-mtv get csv | grep mtv
oc --context site-a -n openshift-mtv get forkliftcontroller,deploy/forklift-controller
oc --context site-a get console.operator cluster -o jsonpath='{.spec.plugins}{"\n"}'                    # includes forklift…
oc --context site-a auth can-i create plans.forklift.konveyor.io -n openshift-mtv                        # yes (students)

    Do it yourself (CLI):

    oc apply -f - <<'YAML'
apiVersion: v1
kind: Namespace
metadata: { name: openshift-mtv }
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata: { name: migration, namespace: openshift-mtv }
spec: { targetNamespaces: [ openshift-mtv ] }
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata: { name: mtv-operator, namespace: openshift-mtv }
spec: { name: mtv-operator, channel: release-v2.11, source: redhat-operators, sourceNamespace: openshift-marketplace }
YAML
oc -n openshift-mtv get csv -w                                  # wait for Succeeded, then:
oc apply -f - <<'YAML'
apiVersion: forklift.konveyor.io/v1beta1
kind: ForkliftController
metadata: { name: forklift-controller, namespace: openshift-mtv }
spec:
  feature_ui_plugin: "true"
  feature_validation: "true"
  feature_volume_populator: "true"
  feature_must_gather_api: "true"
YAML
PLUGIN=$(oc get consoleplugin -o name | grep forklift | cut -d/ -f2); echo "$PLUGIN"
oc patch console.operator cluster --type json -p "[{\"op\":\"add\",\"path\":\"/spec/plugins/-\",\"value\":\"$PLUGIN\"}]"

    Console: 1. Operators → OperatorHub → Migration Toolkit for Virtualization Operator → Install, channel release-v2.11, namespace openshift-mtv. 📸 S-mtv-operatorhub 2. Installed Operators → MTV → ForkliftController → Create. 📸 S-mtv-forkliftcontroller 3. Accept "Web console update is available" and refresh. Migration for Virtualization appears in the menu. 📸 S-mtv-menu

    Red Hat docs: - Installing and using the Migration Toolkit for Virtualization 2.11 [verify link] - MTV prerequisites [verify link] - Migration Toolkit for Virtualization 2.11 documentation

    S.6 The vSphere side: an MTV account, its role, and the vSphere provider¶

    What CI built (automation/customize/mtv_fabric.sh): - On vCenter, an SSO user ovedr-mtv@vsphere.local, with a minted password stored in the class vault and never shown, and a role ovedr-mtv with MTV's minimal privilege set: - power on/off and guest control; - all of Provisioning; - create/remove snapshot; - ChangeTracking (CBT, for warm migration); - datastore browse and file management; - session validation; - Cryptographer decrypt/access.

    It is granted on the vCenter root (/), propagating. CI checks the user can then list the inventory. - A network probe run from inside each cluster before any provider: vCenter 443, every ESXi host on 443 and 902 (MTV's disk copy), and the peer cluster's api-int 6443 and ingress 443. - On each tooled site, Secret + Provider/ovedr-vcenter0<N> (type vsphere, url https://vcenter0<N>…/sdk). It carries user, password, url and cacert: the certificate chain vCenter serves, so TLS is verified, never skipped. - VDDK: retired (2026-10-14). The lab has no VDDK image, so its migrations are cold (Demo 1). Warm migration (Demo 2) is coming soon with storage copy offload on a SAN array instead; why the lab dropped VDDK: Demo 2. S.15 is kept for reference.

    Check:

    oc --context site-a -n openshift-mtv get provider "ovedr-vcenter0$N" \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}  {.spec.url}{"\n"}'
oc --context site-a -n openshift-mtv get provider "ovedr-vcenter0$N" -o jsonpath='{.spec.settings}{"\n"}'   # vddkInitImage?

    Do it yourself (CLI): the vSphere role and user (govc, as a vCenter administrator), then the provider:

    export GOVC_URL="https://vcenter0$N.$DOMAIN" GOVC_USERNAME='administrator@vsphere.local'   # GOVC_PASSWORD from your vault
govc role.create my-mtv VirtualMachine.Interact.PowerOff VirtualMachine.Interact.PowerOn \
  VirtualMachine.State.CreateSnapshot VirtualMachine.State.RemoveSnapshot VirtualMachine.Config.ChangeTracking \
  Datastore.Browse Datastore.FileManagement Sessions.ValidateSession   # … plus Provisioning.*, GuestControl, Cryptographer.*
govc sso.user.create -p '<password>' my-mtv        # the one place a password goes on argv: govc has no other way
govc permissions.set -principal my-mtv@vsphere.local -role my-mtv -propagate=true /

CA="$(openssl s_client -showcerts -servername "vcenter0$N.$DOMAIN" -connect "vcenter0$N.$DOMAIN:443" </dev/null 2>/dev/null \
      | sed -n '/-----BEGIN CERTIFICATE-----/,/-----END CERTIFICATE-----/p')"
oc -n openshift-mtv create secret generic my-vcenter --from-literal=user=my-mtv@vsphere.local \
  --from-literal=password='<password>' --from-literal=url="https://vcenter0$N.$DOMAIN/sdk" --from-literal=cacert="$CA" \
  --from-literal=insecureSkipVerify=false
oc -n openshift-mtv label secret my-vcenter createdForProviderType=vsphere createdForResourceType=providers
oc apply -f - <<YAML
apiVersion: forklift.konveyor.io/v1beta1
kind: Provider
metadata: { name: my-vcenter, namespace: openshift-mtv }
spec: { type: vsphere, url: "https://vcenter0$N.$DOMAIN/sdk", secret: { name: my-vcenter, namespace: openshift-mtv } }
YAML

    Console: 1. vSphere Client: Administration → Roles → New (privileges as above); Single Sign On → Users and Groups → Add; Hosts and Clusters → vCenter → Permissions → Add. 📸 S-vsphere-role · 📸 S-vsphere-permission 2. OpenShift: Migration for Virtualization → Providers → Create Provider → VMware: URL, user, password, and either fetch certificate or paste the CA. 📸 S-mtv-provider-vsphere 3. The provider shows Ready, with VM and host counts. 📸 S-mtv-provider-ready

    Red Hat docs: - VMware prerequisites and privileges for MTV [verify link] - Adding a VMware vSphere source provider [verify link] - Creating a VDDK image [verify link]

    S.7 OpenShift ⇄ OpenShift providers¶

    What CI built: on both sites, ServiceAccount ovedr-mtv-peer in openshift-mtv (bound to cluster-admin, MTV's documented simplest grant for an OpenShift source; the cluster exists only for the booking) and a long-lived token Secret ovedr-mtv-peer-token. On each tooled site, a Provider ovedr-ocp-<peer> (type openshift) whose url and cacert both come from the peer's kubeconfig: the URL is https://api-int.<peer>…:6443 and the CA is the cluster's internal CA.

    💡 Why api-int and not api? After demo-openshift's customize, api.<cluster> serves a public Let's Encrypt certificate. api-int keeps the cluster's internal CA. URL and CA must come from the same place, or TLS verification fails (x509: certificate signed by unknown authority). That happened in this lab, and it is why CI reads both from one kubeconfig.

    Check:

    oc --context site-b -n openshift-mtv get provider "ovedr-ocp-${A#ocp-}" \
  -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}  {.spec.url}{"\n"}'

    Do it yourself (CLI): on the source cluster, create the service account and token. On the destination, create the provider.

    oc --context site-a -n openshift-mtv create sa my-peer
oc --context site-a adm policy add-cluster-role-to-user cluster-admin -z my-peer -n openshift-mtv
oc --context site-a -n openshift-mtv apply -f - <<'YAML'
apiVersion: v1
kind: Secret
type: kubernetes.io/service-account-token
metadata: { name: my-peer-token, namespace: openshift-mtv, annotations: { kubernetes.io/service-account.name: my-peer } }
YAML
TOKEN="$(oc --context site-a -n openshift-mtv get secret my-peer-token -o jsonpath='{.data.token}' | base64 -d)"
URL="https://api-int.$A.$DOMAIN:6443"                  # match the CA below
oc --context site-a config view --raw --minify -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > peer-ca.pem
oc --context site-b -n openshift-mtv create secret generic my-ocp-a --from-literal=token="$TOKEN" \
  --from-literal=url="$URL" --from-file=cacert=peer-ca.pem --from-literal=insecureSkipVerify=false
oc --context site-b -n openshift-mtv label secret my-ocp-a createdForProviderType=openshift createdForResourceType=providers
oc --context site-b apply -f - <<YAML
apiVersion: forklift.konveyor.io/v1beta1
kind: Provider
metadata: { name: my-ocp-a, namespace: openshift-mtv }
spec: { type: openshift, url: "$URL", secret: { name: my-ocp-a, namespace: openshift-mtv } }
YAML
unset TOKEN; rm -f peer-ca.pem

    Console: site B, Migration for Virtualization → Providers → Create Provider → OpenShift Virtualization: URL, service-account token, CA certificate. 📸 S-mtv-provider-ocp

    Red Hat docs: - Adding an OpenShift Virtualization source provider [verify link] - Using service accounts [verify link]

    S.8 Network maps and storage maps¶

    What CI built, per tooled site, in openshift-mtv:

    Map Source → destination Why
    ovedr-vcenter0<N>-net vSphere vm-network → pod network works everywhere; the VM gets a new, cluster-internal address
    ovedr-vcenter0<N>-net-bridge vSphere vm-network → multus default/vmnet<22+N> the VM stays on its VLAN and keeps its own address. Created only when the NAD's bridge is Available
    ovedr-vcenter0<N>-storage datastore coresan01_data00 → this site's class site A: ocs-storagecluster-ceph-rbd-virtualization; site B: nfs-csi
    ovedr-ocp-<peer>-net pod → pod, plus each VLAN NAD present on both sites → the same NAD OVE ⇄ OVE
    ovedr-ocp-<peer>-storage the peer's class → this site's class OVE ⇄ OVE converts ODF ⇄ NFS: the disks are copied into the destination's storage

    Check:

    oc --context site-a -n openshift-mtv get networkmap,storagemap
oc --context site-a -n openshift-mtv get storagemap "ovedr-vcenter0$N-storage" -o jsonpath='{.spec.map}{"\n"}' | jq .

    Do it yourself (CLI):

    P="ovedr-vcenter0$N"
oc --context site-a apply -f - <<YAML
apiVersion: forklift.konveyor.io/v1beta1
kind: NetworkMap
metadata: { name: my-net-bridge, namespace: openshift-mtv }
spec:
  provider: { source: { name: $P, namespace: openshift-mtv }, destination: { name: host, namespace: openshift-mtv } }
  map: [ { source: { name: vm-network }, destination: { type: multus, name: vmnet${VLAN}, namespace: default } } ]
---
apiVersion: forklift.konveyor.io/v1beta1
kind: StorageMap
metadata: { name: my-storage, namespace: openshift-mtv }
spec:
  provider: { source: { name: $P, namespace: openshift-mtv }, destination: { name: host, namespace: openshift-mtv } }
  map: [ { source: { name: coresan01_data00 }, destination: { storageClass: ocs-storagecluster-ceph-rbd-virtualization } } ]
YAML

    Console: Migration for Virtualization → Network maps → Create (source network → Multus: default/vmnet); Storage maps → Create (datastore → storage class). 📸 S-networkmap · 📸 S-storagemap

    S.14 How the two clusters are joined: ACM, Submariner, then ODF disaster recovery¶

    Two clusters become one DR pair in three layers, and each layer needs the one before it. Demo 1c (moving a VM between clusters) needs only MTV's providers (S.7). Demo 4 (ODF Regional-DR) needs all three layers.

      layer 1  ACM       one hub MANAGES both clusters        ManagedCluster, ManagedClusterSet
  layer 2  Submariner the clusters' pod/service networks  submariner add-on, Broker, (Globalnet)
           can reach each other
  layer 3  ODF DR    Ceph RBD mirroring between the two   ODF Multicluster Orchestrator: MirrorPeer,
           ODF clusters, driven from the hub              DRCluster, DRPolicy; per app: DRPlacementControl

    Layer 3: linking ODF for replication (Demo 4)¶

    Each site runs its own Ceph cluster (ODF). Replication links the two so every protected RBD image (a VM disk) on the primary is mirrored to the other site as snapshots on a schedule. The link has four parts, all created from the hub:

    Part What it is Created by
    MCG (NooBaa) on both sites object storage where Ramen keeps each protected app's DR metadata dr_fabric.sh step 1 (ODF ships it off here)
    MirrorPeer pairs the two StorageClusters: exchanges Ceph keys/endpoints, turns on RBD mirroring (rbd-mirror daemons) between them, over Submariner dr_fabric.sh step 3 (or the console's DRPolicy wizard)
    DRCluster × 2 the hub's view of each site as a DR peer (its S3 profile, fencing state) ODF Multicluster Orchestrator, from the MirrorPeer
    DRPolicy "these two clusters, async, every 15m" dr_policy.sh (<A>-<B>-15m)

    Then each protected application (Demo 4: the ovedr-app + student namespaces) gets a DRPlacementControl on the hub, which tells Ramen which cluster is primary and drives Failover/Relocate.

    Prerequisites, in order: both clusters managed by the hub (layer 1) · Submariner connected (layer 2) · ODF Ready on both sites · then the parts above.

    S.15 VDDK: the one piece the customer supplies (Broadcom licence)¶

    Retired, 2026-10-14. This lab no longer uses VDDK: it can't obtain the kit, and Demo 2 moves to storage copy offload (why). This section stays as reference for a customer who already holds a VDDK copy and the right to use it.

    What it is. The VMware Virtual Disk Development Kit (VDDK) is VMware's library for reading a VM's disks straight from ESXi. MTV uses it to copy disks, and for a warm migration to copy only the blocks that changed since the last pass (VMware's Changed Block Tracking, Demo 2). Warm migration needs it; a cold migration works without it, only slower [verify: MTV 2.11 cold path without VDDK].

    Why you supply it. VDDK is Broadcom's software, and its licence does not allow Red Hat, Paragon Micro or anyone else to redistribute it. So OpenShift doesn't ship it, and neither does this lab's code: each customer downloads VDDK themselves from Broadcom's developer portal with their own account, accepts the licence, builds a small container image from it, and keeps that image in their own private registry. Never put the tarball or the image in git or a public registry. In a real migration project this is one of the first prerequisites to arrange.

    How to build it (Red Hat's procedure):

    1. Download VDDK 8.0.x for Linux (VMware-vix-disklib-<version>.x86_64.tar.gz) from Broadcom's developer portal.
    2. Unpack it next to this Containerfile:
    FROM registry.access.redhat.com/ubi8/ubi-minimal
USER 1001
COPY vmware-vix-disklib-distrib /vmware-vix-disklib-distrib
RUN mkdir -p /opt
ENTRYPOINT ["cp", "-r", "/vmware-vix-disklib-distrib", "/opt"]
    1. Build and push it to a private registry. On OpenShift, the cluster's own registry works, with no tool on your laptop:
    tar -xzf VMware-vix-disklib-*.x86_64.tar.gz                  # → vmware-vix-disklib-distrib/
oc -n openshift-mtv new-build --name vddk --binary --strategy docker
oc -n openshift-mtv start-build vddk --from-dir=. --follow   # the directory with the Containerfile and the unpacked kit
oc -n openshift-mtv get istag vddk:latest                    # image-registry.openshift-image-registry.svc:5000/openshift-mtv/vddk:latest

    MTV's migration pods run in the target namespace, so let every service account pull from openshift-mtv:

    oc -n openshift-mtv policy add-role-to-group system:image-puller system:serviceaccounts
    1. Point the vSphere provider at it. Console: Migration for Virtualization → Providers → your vSphere provider → VDDK init image → edit. CLI:
    oc -n openshift-mtv patch provider "ovedr-vcenter0$N" --type merge \
  -p '{"spec":{"settings":{"vddkInitImage":"image-registry.openshift-image-registry.svc:5000/openshift-mtv/vddk:latest"}}}'

    How this lab does it (automation/customize/vddk.sh, job vddk, after MTV is installed):

    1. Once per VDDK version, the operator downloads the kit with the lab's Broadcom account and runs automation/tools/vddk_image.sh <kit>. It builds the image above and saves it in the lab's private registry (never git, never public: the script refuses to finish if the image can be read without credentials). The image holds the unpacked kit, so it is also the lab's only stored copy of the download.
    2. Every booking, on each cluster that runs MTV: a Docker BuildConfig whose Containerfile is just FROM <the saved image> copies it into the cluster's own registry as openshift-mtv/vddk:<version>, with a short-lived read-only pull credential that is deleted when the build ends. Then the image-puller grant above.
    3. The vSphere provider gets vddkInitImage: image-registry.openshift-image-registry.svc:5000/openshift-mtv/vddk:<version>, and the run's readiness table shows Demo 2 ready.

    So nothing is redistributed, the licensed file leaves the lab's private storage only into the lab's own clusters, and a booking never waits on a download. If no saved image exists yet, the vddk job warns, Demo 2 shows blocked and the warm plans show VDDKInitImageUnavailable (Demo 2 §2.5); the cold class runs as normal.

    Where Broadcom keeps it: VDDK moved to Broadcom's developer portal (developer.broadcom.com → SDKs → VMware Virtual Disk Development Kit), behind a Broadcom sign-in. Older VMware download links no longer work. Use a VDDK version your vSphere release and your MTV release both support (Red Hat's MTV prerequisites list them).

    Check:

    oc --context site-a -n openshift-mtv get provider "ovedr-vcenter0$N" -o jsonpath='{.spec.settings.vddkInitImage}{"\n"}'   # the image
oc --context site-a -n openshift-mtv get plan -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.status.conditions[?(@.type=="VDDKInitImageUnavailable")].status}{"\n"}{end}'   # empty: no plan lacks it
